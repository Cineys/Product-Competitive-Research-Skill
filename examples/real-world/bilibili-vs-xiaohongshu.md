# 案例 B：B站与小红书

本案例来自 2026-10-11 的一次 V1.1 真实网页研究。以下内容均为模型原始回答节选，删节处不补写新结论。该运行发生在来源身份规则补充之前。

## 明确的研究请求

> 请深入比较 B站和小红书在收藏内容、查找已收藏内容，以及后续重新使用这些内容方面的产品体验。
>
> 重点关注用户收藏学习资料、攻略或实用内容后的再次查找与使用。
>
> 我希望通过这次分析，寻找内容产品在收藏管理和内容复访方面值得借鉴的设计思路。

模型没有再次澄清，而是自主采用用户任务链：

> **保存 → 组织 → 找回内容 → 定位有用部分 → 实际使用**

## 主要发现（原文节选）

> **最值得借鉴的区别是：B站的收藏更容易接上“继续观看、定位片段、复习知识”的流程；小红书的收藏更贴近“归集攻略、现场查阅、共同决策”的流程。** 对内容产品来说，应同时考虑保存整条内容、找回具体信息，以及把信息用于任务这三个层次。

> **允许用户先轻松保存，再逐步整理；分类应帮助查找，而不能成为查找的前置条件。**

> **让用户用自己的记忆找内容，并在结果中解释“为什么找到了这条”。**

> 两者共同暴露出的产品机会是：**用户要保存的，可能是整条内容中的一张图、一段解释或一步操作。** 因而收藏可以同时保存来源和用户选中的位置。

## 具体设计建议（原文节选）

> 其中，最适合作为第一轮原型的是一个**带使用线索的收藏卡片**：

| 卡片信息 | 示例 |
|---|---|
| 原始来源 | 某软件操作教程 |
| 收藏理由 | 做季度报告时用来去重 |
| 保存位置 | 视频12:40 |
| 所属任务 | 季度报告 |
| 再次使用入口 | 直接跳到该步骤 |
| 使用状态 | 常用参考 |

> 这是综合两款产品思路提出的方案：保留内容来源，用具体位置降低复习成本，用任务和理由帮助再次找回。

## 证据限制与后续诊断

原回答明确说明：

> 没有登录两款 App 做同版本实测；部分功能依据历史教程或第三方体验记录，以下明确标注，不能视为当前所有账号的操作说明。

> 本次研究的主要缺口是：两款 App 当前收藏搜索范围、正文／字幕／图片文字索引、批量管理，以及跨端状态恢复未得到同版本实测验证。

后续审计更正了两点：

1. 报告中的 `https://www.bilibili.com/opus/425087778171832965` 已被实际读取。模型先打开旧 `read` URL，工具重定向到该 `opus` URL并返回正文；精简日志没有保留重定向目标，导致此前“未读取 URL”的 P0 判断错误。原始 session rollout 已证明正文读取，该问题属于审计观测误差。
2. 原回答把 B站域名下的一篇历史文章称为“B站官方历史功能说明”，但日志不足以证明发布主体属于官方。这一 P1 问题促成了规则补充：官方域名不等于官方发布主体；无法确认时应使用中性描述。修复后的模型行为尚未重新验证。
